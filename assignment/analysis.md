- 대상: `과제_장바구니주문결제_지원자배포.pdf`, `legacy_db.sql`. PDF 는 저장소에 두지 않으며 내용은 [assignment.md](assignment.md)에 옮겨 두었다
- 검증 방법: `legacy_db.sql`을 임시 SQLite DB(3.51.0)에 적재해 정합성 쿼리와 동시성 관련 동작을 직접 실행했다. 아래에서 "확인함"은 실행 결과이고, "추정"은 데이터만으로는 단정할 수 없는 해석이다.
- 이 문서는 분석까지만 다룬다. 설계 결정은 DESIGN.md / ADR에서 내린다.

## 1. 과제 정리

### 1.1 평가 관점

- 코드 완성도가 아니라 **설계와 판단**을 본다.
- 요구사항은 의도적으로 열려 있다. 즉 빈 곳은 **가정을 세우고 근거를 밝히는 것**이 채점 대상이다.
- AI 사용은 자유지만, 무엇을 맡기고 무엇을 직접 판단했는지를 따로 제출해야 한다.

### 1.2 배경에서 주어진 조건

| 조건 | 설계에 주는 의미 |
|---|---|
| 점진 전환 | 한 번에 갈아끼우는 방식은 배제된다 |
| 10년 된 레거시, 문서·개발자 없음 | 레거시의 동작은 스키마와 데이터로 추론해야 하고, 추론은 가정으로 남겨야 한다 |
| 서비스는 멈출 수 없다 | 점검 시간을 두는 전환, 긴 잠금이 필요한 이관은 쓸 수 없다 |
| 세일·오픈 시점에 동일 상품으로 주문이 몰린다 | 같은 상품 행에 대한 동시 쓰기(재고)가 핵심 경합 지점이다 |
| 가격은 운영 중 수시로 바뀐다 | 장바구니에 담은 시점과 주문 시점의 가격이 다를 수 있다 |
| 한 결제에 PG·제휴 포인트·내부 포인트·쿠폰이 함께 쓰인다 | 수단별 성공/실패가 갈릴 수 있고, 외부 호출은 DB 트랜잭션으로 묶을 수 없다 |
| 전환 기간 동안 레거시 DB와 신규 시스템이 공존한다 | 두 저장소에 걸친 쓰기와, 레거시 쪽 독자·작성자가 여전히 살아 있다는 점을 다뤄야 한다 |

### 1.3 요구사항

1. 장바구니 → 주문 → 결제 흐름을 신규 시스템 관점에서 재설계
2. 레거시 DB와 신규 DB를 어떻게 나눌지, 공존 기간에 데이터를 어떻게 다룰지 결정하고 근거 제시
3. 가장 위험하다고 판단한 지점 **하나**를 골라 실행 가능한 코드와 테스트로 증명 (전체 구현 불필요)

### 1.4 제출물

| 제출물 | 담아야 할 것 |
|---|---|
| `DESIGN.md` | 문제 정의, 전체 구조, 레거시/신규 DB 분리 결정과 근거, 세운 가정 |
| 핵심 구현 + 테스트 | 요구사항 3의 코드와 테스트, 실행 방법은 `README.md` |
| `adr/` | 핵심 결정 **최소 3건**. 각 건마다 맥락 / 고려한 대안 / 선택과 근거 / 버린 이유와 trade-off |
| `AI_REFLECTION.md` | AI에 맡긴 것, 직접 판단한 것, 거부·수정한 제안과 이유 |
| `prompts/used_prompts.md` | 사용한 프롬프트 원문 |

### 1.5 기술 제약

- 언어는 Kotlin (필수)
- 저장소는 SQLite3, 별도 인프라 없이 실행 가능해야 한다
- 레거시 DB와 신규 DB를 어떻게 표현할지(스키마, 분리 방식)는 지원자가 정한다
- 프레임워크·라이브러리·프로젝트 구조는 자유
- 핵심 구현은 반드시 실행 가능해야 한다

### 1.6 제출 형식과 기한

- GitHub 레포지토리 또는 ZIP
- 제공일로부터 3일

### 1.7 실격 요건

1. 제출한 코드가 실행되지 않으면 실격
2. AI 프롬프트를 제출하지 않으면 실격
3. 프롬프트는 링크로 낼 수 없고 `used_prompts.md`만으로 확인 가능해야 한다

실격을 피하기 위해 지금부터 챙길 것:

- 프롬프트는 대화가 끝난 뒤 복원하기 어렵다. **이번 요청을 포함해 매 프롬프트를 그때그때 `prompts/used_prompts.md`에 원문으로 적어 둔다.**
- "실행 가능"은 채점자 환경 기준이다. Gradle Wrapper를 포함하고, 깨끗한 클론에서 `./gradlew test` 한 번으로 도는지 확인한다. 현재 이 PC에는 JDK 17과 Gradle이 있고 `kotlinc`는 없으므로 Gradle Kotlin 플러그인으로 빌드하는 구성이 맞다.
- SQLite 파일은 테스트가 매번 `legacy_db.sql`에서 새로 만들도록 해서, 남은 파일 상태에 따라 결과가 달라지지 않게 한다.

## 2. legacy_db.sql 검토

### 2.1 스키마 구조상 문제

#### 전 테이블 공통

| 문제 | 영향 |
|---|---|
| 외래 키가 하나도 없다 | 없는 회원·상품·주문을 가리키는 행이 들어갈 수 있다 |
| PK 외에 NOT NULL, CHECK, UNIQUE가 없다 | 음수 재고, 음수 포인트, 정의되지 않은 상태 코드, 금액 불일치를 DB가 막지 못한다 |
| 보조 인덱스가 없다 | `TB_PAY.ORD_NO`, `TB_ORDER.MBR_NO`, `TB_CART.MBR_NO` 조회가 전부 풀 스캔이다 |
| 일시를 `'YYYYMMDDHHMISS'` 문자열로 저장한다 | 타임존이 없고, 형식이 깨진 값도 들어간다 |
| 상태를 설명 없는 코드 문자열로 둔다 | 허용 값과 전이 규칙이 애플리케이션 코드에만 있다 |
| 변경 이력이 없다 | 재고, 포인트, 가격, 주문 상태 모두 현재 값만 남는다. 사후 대사가 불가능하다 |
| 낙관적 잠금용 버전 컬럼이 없다 | 읽고 계산해서 덮어쓰는 방식의 갱신 유실을 감지할 수 없다 |

#### 테이블별

**TB_GOODS**
- 가격(`SALE_PRC`), 재고(`STOCK_QTY`), 판매 상태(`SALE_STAT`)가 한 행에 있다. 변경 주기와 변경 주체가 전혀 다른 값들이 같은 행을 두고 경합한다.
- 품절 여부가 `STOCK_QTY = 0`과 `SALE_STAT = '02'` 두 곳에 표현된다. 한쪽만 갱신되면 어긋난다.
- 가격 이력과 적용 기간이 없다. "이 시각에 유효했던 가격"을 알 수 없다.
- `UPD_DT`가 가격 변경 시각인지 재고 변경 시각인지 구분되지 않는다.

**TB_MEMBER**
- 포인트가 잔액(`POINT_AMT`) 하나뿐이다. 적립·사용 원장이 없어서 잔액이 맞는지 검증할 방법이 없다.
- 회원 정보와 포인트 잔액이 같은 행이라, 포인트 차감이 회원 행을 잠근다.
- `MBR_ID`에 UNIQUE가 없다.

**TB_CART**
- `(MBR_NO, GOODS_CD)` UNIQUE가 없어 같은 상품이 여러 행으로 담길 수 있다.
- 담은 시점 가격이 없다. 가격 변동을 사용자에게 알릴 근거가 없다.

**TB_ORDER**
- `ORD_AMT - DC_AMT = PAY_AMT` 관계를 보장하는 제약이 없다.
- 상태가 접수/결제대기/결제완료/취소 네 개뿐이다. 부분 취소, 환불 진행 중, 결제 실패를 표현할 수 없다.
- 주문번호가 `ORD + 날짜 + 3자리 일련번호`로 보인다(추정). 하루 999건이 한계이고, 일련번호 채번이 동시 요청에서 충돌할 수 있다. 신규 시스템이 같은 규칙으로 번호를 만들면 레거시와 충돌한다.
- 중복 요청을 걸러낼 멱등 키가 없다.

**TB_PAY**
- PG, 카드, 가상계좌, 내부 포인트, 제휴 포인트, 쿠폰이 한 행의 컬럼으로 펼쳐져 있다. 수단이 추가되면 컬럼이 늘고, 대부분 NULL이다.
- 수단별 상태가 없다. `PAY_STAT` 하나가 행 전체를 대표하므로 **"PG는 승인됐는데 제휴 포인트는 실패"라는 상태를 저장할 수 없다.** 과제 배경의 복합 결제와 정면으로 부딪히는 지점이다.
- 한 결제에 쿠폰 1장, PG 수단 1개, 제휴사 1곳만 담을 수 있다.
- `PAY_STAT = 'C'`가 두 가지 뜻으로 쓰인다. 원 결제 행을 취소로 덮어쓴 경우와, 취소 거래를 새 행으로 추가한 경우다(2.2의 D3, D4).
- 취소 행이 어느 원 결제를 취소한 것인지 가리키는 컬럼이 없다.
- 주문과 결제가 1:N인데 `ORD_NO`에 인덱스도 제약도 없다.
- `PG_APPROVE_NO`에 UNIQUE가 없어 같은 승인 건이 두 번 기록되는 것을 막지 못한다.

**TB_ORDER_ITEM**
- 품목별 상태와 취소 수량이 없다. 부분 취소가 어느 품목에서 일어났는지 기록할 곳이 없다.
- 쿠폰 할인이 품목별로 어떻게 배분됐는지 없다. 부분 환불 금액을 계산할 근거가 없다.
- 상품명 스냅샷이 없다.

**TB_COUPON**
- 정액 할인만 표현된다. 유효기간, 최소 주문 금액이 없다.
- 쿠폰 사용 사실이 `TB_COUPON.USE_YN/USE_ORD_NO`, `TB_PAY.CPN_NO/CPN_AMT`, `TB_ORDER.DC_AMT` 세 곳에 중복된다. 주문 취소 때 세 곳을 모두 고쳐야 한다.
- `USE_YN`을 `'N'`에서 `'Y'`로 바꾸는 갱신이 조건 없이 이뤄지면 같은 쿠폰이 두 주문에 쓰일 수 있다.

### 2.2 데이터 정합성

먼저 **맞는 것**(확인함):

- 6개 주문 모두 `ORD_AMT`가 품목 합계(`ORD_QTY × ORD_PRC`)와 일치한다.
- 6개 주문 모두 `ORD_AMT - DC_AMT = PAY_AMT`가 성립한다.
- 각 주문의 원 결제 행에서 `PG_AMT + PNT_AMT + MILE_AMT = PAY_AMT`가 성립한다. 즉 레거시는 **쿠폰은 할인으로, 포인트와 제휴 포인트는 결제 수단으로** 취급한다.
- 쿠폰 3장 모두 쿠폰 소유 회원과 주문 회원이 같고, 쿠폰 금액이 주문의 `DC_AMT`와 같다.
- 주문 품목의 `ORD_PRC`는 모두 현재 `SALE_PRC`와 같다. 가격 변동 사례는 샘플에 없다.
- 고아 행(없는 회원·상품·주문을 가리키는 행)은 없다.

| D11 | `TB_ORDER` ORD20260301003, `TB_PAY` PAY_SEQ=3 | 가상계좌 입금 대기 주문이다. 정합성은 맞지만 입금 기한이 `20260303235959`인 **진행 중 거래**다. | 정상. 다만 전환 시점에 이런 진행 중 주문을 누가 마무리하는지 정해야 한다 |
| D12 | `TB_ORDER` 전체 | 상태 `'00'` 접수는 정의만 있고 쓰인 행이 없다. | 참고 |

요약하면 이 데이터가 보여 주는 것은 세 가지다.

1. **주문 상태와 결제 상태가 따로 논다** (D1). 두 테이블을 한 트랜잭션으로 묶지 않았거나, 중간 실패를 복구하지 않는다.
2. **취소·환불 경로가 부실하다** (D2~D6). 결제 수단별 환불 배분과 쿠폰 환원이 일관되지 않다.
3. **재고와 포인트는 검증할 근거 자체가 없다** (D8, D9).

따라서 레거시의 주문·결제 상태를 신규 시스템이 그대로 믿으면 안 되고, 이관이나 조회 시 "주문 상태와 결제 행을 교차 확인한다"는 규칙이 필요하다.

## 3. 가장 위험한 지점 후보

### 3.1 SQLite에서의 테스트 가능성 (공통 전제)

직접 실행해 확인한 SQLite 3.51.0의 동작이다.

| 항목 | 결과 |
|---|---|
| 조건부 UPDATE (`... SET STOCK_QTY = STOCK_QTY - ? WHERE STOCK_QTY >= ?`) | 동작한다. 재고 3에서 2개 차감은 `changes() = 1`, 이어서 다시 2개 차감은 `changes() = 0` |
| `UPDATE ... RETURNING` | 지원된다 |
| `SELECT ... FOR UPDATE` | **문법 오류.** 행 잠금이 없다 |
| `BEGIN IMMEDIATE` | DB 파일 전체에 쓰기 잠금을 건다. 다른 커넥션의 쓰기는 `database is locked`로 즉시 실패한다 |
| `busy_timeout` | 설정하면 실패 대신 잠금이 풀릴 때까지 기다렸다가 성공한다 |
| WAL 모드 | 켤 수 있다. 읽기와 쓰기가 서로 막지 않는다 |
| `ATTACH`로 두 파일을 한 트랜잭션에 묶기 | 동작한다. 롤백 시 두 파일 모두 원복됐다 |

여기서 나오는 제약 세 가지는 DESIGN.md에 가정으로 명시해야 한다.

- **SQLite는 쓰기가 DB 파일 단위로 직렬화된다.** 그래서 "행 잠금 경합"이나 "교착"은 재현되지 않는다. 반면 "읽고 → 계산하고 → 덮어쓰기"로 생기는 갱신 유실은 커넥션을 여러 개 쓰면 그대로 재현된다. 테스트가 증명하는 것은 **알고리즘의 정확성**이지 운영 DB에서의 처리량이 아니다.
- 다중 스레드 테스트는 스레드마다 커넥션을 따로 열고, `busy_timeout`을 주고, 파일 DB를 써야 한다. 인메모리 DB는 커넥션마다 별개의 DB가 된다.
- `ATTACH`의 다중 파일 원자 커밋은 SQLite에만 있는 기능이다. 실제 레거시 DB와 신규 DB는 서로 다른 서버일 것이므로, 이 기능에 기대어 "두 DB가 한 트랜잭션"이라고 설계하면 과제 의도(공존 기간의 불일치 처리)를 피해 가는 셈이 된다. 두 DB는 **별도 파일, 별도 커넥션**으로 두는 편이 정직하다.

### 3.2 후보

#### 후보 A. 동일 상품 동시 주문 시 재고 초과 판매

- 위험: 세일 시점에 재고 3개인 상품에 100건이 동시에 들어오면, 재고를 읽고 확인한 뒤 차감하는 방식은 3개보다 많이 판다. 레거시에는 음수 재고를 막는 제약이 없다.
- 근거: 배경의 "동일 상품으로 주문이 몰립니다", `TB_GOODS`에 CHECK 없음, G002 재고 3.
- SQLite 테스트: **가능.** 스레드 N개가 각자 커넥션으로 동시에 주문하고, 성공 건수 = 초기 재고, 최종 재고 ≥ 0을 검증한다. 잘못된 구현(조회 후 덮어쓰기)이 실패하는 것을 대조군으로 보여 줄 수 있다.
- 한계: 운영 DB의 행 잠금 경합과 성능은 보여 줄 수 없다. 문제 자체가 잘 알려져 있어 판단의 깊이를 드러내기는 상대적으로 어렵다.

#### 후보 B. 복합 결제의 부분 실패와 보상

- 위험: 쿠폰 사용, 포인트 차감, 제휴 포인트 승인, PG 승인 중 일부만 성공하면 돈은 나갔는데 주문은 없거나, 주문은 됐는데 돈은 안 받은 상태가 된다. D1(결제 없는 완료 주문)과 D3(포인트 몫 환불 불일치)이 레거시에서 이미 이 문제가 일어났음을 보여 준다.
- 근거: 배경의 복합 결제 조건, `TB_PAY`에 수단별 상태 없음.
- SQLite 테스트: **가능.** PG와 제휴사는 가짜 구현으로 두고 실패·타임아웃·보상 실패를 주입한다. 각 지점에서 실패시킨 뒤 "승인된 채 남은 수단이 없다", "포인트와 쿠폰이 원복됐다"를 검증한다.
- 한계: 외부 시스템이 가짜이므로 가정(취소 API가 멱등하다 등)을 명시해야 한다.

#### 후보 C. 레거시 DB와 신규 DB에 걸친 쓰기의 부분 반영

- 위험: 주문은 신규 DB에 기록됐는데 레거시의 재고 차감이 안 됐거나, 그 반대. 두 커밋 사이에서 프로세스가 죽으면 어느 쪽도 스스로는 불일치를 알지 못한다.
- 근거: 배경의 "레거시 DB와 신규 시스템은 공존", 요구사항 2가 통째로 이 주제다.
- SQLite 테스트: **가능.** DB 파일 두 개를 별도 커넥션으로 열고, 두 커밋 사이에 예외를 던지거나 실행을 중단시킨 뒤 복구 로직을 돌려 양쪽이 수렴하는지 검증한다. 같은 요청을 다시 실행해도 재고가 두 번 빠지지 않는지도 확인한다.
- 한계: 실제 프로세스 강제 종료 대신 실패 주입으로 흉내 낸다. 네트워크 분단은 재현하지 않는다.

#### 후보 D. 중복 요청과 멱등성

- 위험: 결제 버튼 중복 클릭, 타임아웃 후 재시도, PG 콜백 중복 수신으로 같은 주문이 두 번 결제되거나 재고가 두 번 빠진다. 레거시에는 멱등 키도, 승인번호 UNIQUE도 없다.
- SQLite 테스트: **가능.** UNIQUE 제약과 동시 요청으로 검증한다.
- 한계: 단독으로는 범위가 좁다. B나 C의 일부로 넣는 편이 자연스럽다.

### 3.3 비교

| 후보 | 과제 배경과의 연결 | 레거시 데이터의 증거 | SQLite 재현 충실도 | 판단을 드러낼 여지 |
|---|---|---|---|---|
| A 재고 초과 판매 | 직접 언급됨 | 간접 (D8) | 정확성은 높음, 경합은 재현 안 됨 | 보통 |
| B 복합 결제 부분 실패 | 직접 언급됨 | 강함 (D1, D3) | 가짜 외부 시스템에 의존 | 높음 |
| C 두 DB 부분 반영 | 직접 언급됨, 요구사항 2 | 간접 (D1) | 높음 | 높음 |
| D 멱등성 | 간접 | 약함 | 높음 | B·C에 포함시키는 편이 낫다 |

검토 의견: **C를 주제로 하고 그 안에서 A의 조건부 차감과 D의 멱등성을 함께 쓰는 구성**이 요구사항 2와 3을 한 번에 연결한다. "신규 DB에 주문 생성 + 레거시 DB에서 재고 차감" 시나리오 하나로 동시성, 부분 반영, 재시도를 모두 보여 줄 수 있다. B는 설계 문서에서 다루고 구현은 범위 밖으로 두는 것이 3일 일정에 맞다. 최종 선택은 직접 내려야 하고, 그 이유가 ADR 한 건이 된다.

**결정: 후보 C(레거시 DB와 신규 DB에 걸친 쓰기의 부분 반영)를 구현 대상으로 선택했다.** 구현 범위는 4.6의 구조이며, 후보 A의 조건부 재고 차감과 후보 D의 멱등성을 그 안에 포함한다. 후보 B는 DESIGN.md에서 설계로만 다룬다.

## 4. 확인 요청 검토

### 4.1 "무중단 + 공존"은 순차 전환을 뜻하는가

**맞다.** 배경 첫 문장이 "점진 전환"이라고 직접 말하고, "서비스는 멈출 수 없다"와 "전환 기간 동안 공존한다"가 이를 뒷받침한다. 한 번에 모두 옮기는 방식은 과제 의도에서 벗어난다.

다만 해석을 한 단계 더 넓혀야 한다. 원문은 "레거시 **DB**와 신규 **시스템**이 공존한다"이다. 여기서 따라 나오는 것:

1. **레거시 DB를 읽고 쓰는 다른 주체가 계속 있다.** 관리자 화면, 정산, CS, 배송 연동, 그리고 아직 전환되지 않은 레거시 주문 경로가 같은 테이블을 계속 쓴다. 신규 시스템은 레거시 DB의 유일한 사용자가 아니다.
2. **데이터를 옮기는 것과 트래픽을 옮기는 것은 별개다.** 무중단이 되려면 일부 트래픽만 신규로 보내고, 문제가 생기면 되돌릴 수 있어야 한다.
3. **전환 중인 거래가 있다.** D11처럼 며칠 뒤에 끝나는 가상계좌 주문이 전환 시점을 걸쳐 존재한다.

레거시 애플리케이션이 공존 기간에 주문을 계속 만드는지는 과제에 없다. **가정으로 정해 DESIGN.md에 적어야 하는 항목**이다. 보수적으로는 "레거시 주문 경로도 한동안 살아 있고, 같은 재고를 차감한다"로 두는 편이 안전하다.

### 4.2 재고·포인트·쿠폰은 레거시, 주문·결제·장바구니는 신규

**방향은 타당하다.** 좋은 점:

- 과제가 재설계를 요구한 범위(장바구니·주문·결제)와 신규 DB의 소유 범위가 일치한다.
- 재고·포인트·쿠폰은 레거시의 다른 기능도 쓰는 공유 자원이다. 원본을 한 곳에 두면 "누가 진짜 값인가" 문제가 생기지 않는다.
- 세 자원이 모두 레거시에 있으므로 **재고 차감, 포인트 차감, 쿠폰 사용을 레거시 쪽 로컬 트랜잭션 하나로 묶을 수 있다.** DB 간 불일치 지점이 "신규 주문 기록 대 레거시 자원 차감" 한 군데로 줄어든다.
- `TB_ORDER`/`TB_PAY`의 구조적 한계(수단별 상태 없음, 부분 취소 표현 불가)를 신규 스키마에서 바로 해결할 수 있다.

보완이 필요한 점:

1. **모든 주문이 DB 간 쓰기가 된다.** 주문은 신규, 재고는 레거시이므로 가장 뜨거운 경로가 곧 가장 취약한 경로다. 4.6의 설계가 전제 조건이다.
2. **레거시 쪽 독자가 신규 주문을 못 본다.** 정산·CS·배송이 `TB_ORDER`/`TB_PAY`를 읽고 있다면 신규 주문이 사라진 것처럼 보인다. 선택지는 (a) 신규 주문을 레거시 형태로 역방향 기록한다, (b) 해당 독자들이 신규 쪽을 읽도록 함께 전환한다, (c) 범위 밖이라고 가정한다. 과제 규모에서는 (a)를 방향으로 제시하고 구현은 생략하는 것이 현실적이다.
3. **기존 주문 이력의 위치.** 과거 주문은 레거시에 그대로 두고 조회 시 양쪽을 합칠지, 일괄 이관할지 정해야 한다. 2.2에서 보았듯 레거시 주문 데이터는 그대로 옮기기에 품질이 낮다. "이관하지 않고 읽기 전용으로 남긴다"가 위험이 작다.
4. **진행 중 주문.** ORD20260301003 같은 결제 대기 주문은 생성한 쪽이 끝까지 처리한다는 규칙이 단순하다.
5. **장바구니는 성격이 다르다.** 금전 정합성과 무관하고 잃어도 피해가 작다. 가장 먼저 옮기기 좋은 대상이지만, 레거시 화면이 `TB_CART`를 읽는다면 전환 중 사용자가 장바구니가 비어 보이는 문제가 생긴다.
6. **포인트는 `TB_MEMBER` 안에 있다.** 포인트를 레거시에 둔다는 것은 회원 행을 신규 시스템이 갱신한다는 뜻이다. 레거시가 회원 행 전체를 덮어쓰는 방식이라면 포인트 차감이 유실될 수 있다(4.4의 가정과 같은 문제).
7. **레거시 접근은 한 곳으로 모은다.** 신규 코드가 `TB_*` 테이블을 여기저기서 직접 건드리지 않고, 재고·포인트·쿠폰 각각의 인터페이스 뒤에 숨긴다. 나중에 이 자원들을 신규로 옮길 때 구현만 바꾸면 된다. "이후 단계에서 순차 이전"이라는 계획이 설득력을 가지려면 이 경계가 있어야 한다.

### 4.3 주문 폭주 처리: 큐 직렬화 / DB 잠금 / 조건부 UPDATE

| | 큐로 직렬화 | DB 잠금 (비관적 잠금) | 조건부 UPDATE |
|---|---|---|---|
| 방식 | 주문 요청을 상품별 큐에 넣고 한 건씩 처리 | 재고 행을 잠그고 읽은 뒤 차감 | `SET STOCK_QTY = STOCK_QTY - n WHERE GOODS_CD = ? AND STOCK_QTY >= n`, 영향 행 수로 성공 판정 |
| 장점 | 순간 부하를 흡수해 DB를 보호한다. 선착순이 보장된다. 대기열 UX를 붙일 수 있다 | 이해하기 쉽다. 읽은 값에 기반한 복잡한 검증을 같은 트랜잭션에서 할 수 있다 | 문장 하나가 원자적이다. 잠금 보유 시간이 가장 짧다. 추가 인프라가 없다. 음수 재고가 구조적으로 불가능하다 |
| 단점 | 인프라가 추가된다(과제 제약과 충돌). 응답이 비동기가 되어 흐름과 UX가 복잡해진다. 큐 자체의 유실·중복 처리를 다뤄야 한다 | 인기 상품 행에서 대기가 줄을 선다. 트랜잭션이 길어지면(외부 호출 포함 시) 치명적이다. 여러 상품 주문에서 교착이 생길 수 있다 | 실패 사유가 "재고 부족"으로만 나온다. 선착순이 엄밀하지 않다. 여러 상품 주문은 일부만 성공할 수 있어 트랜잭션으로 묶어야 한다 |
| 레거시 공존 | **레거시 주문 경로는 큐를 거치지 않는다.** 큐만으로는 정확성이 보장되지 않는다 | 레거시도 같은 방식으로 잠가야만 유효하다 | 레거시가 어떻게 쓰든 **신규 쪽 차감은 음수를 만들지 않는다** |
| SQLite | 테스트는 가능하나 큐를 직접 흉내 내야 한다 | `SELECT FOR UPDATE`가 없다. `BEGIN IMMEDIATE`로 DB 전체를 잠그는 것이 유일한 대응이다 | 그대로 동작한다 (확인함) |

검토 의견:

- 세 가지는 서로 배타적이지 않다. **정확성의 최종 방어선은 DB에서의 조건부 UPDATE로 두고, 큐는 필요할 때 그 앞에 붙이는 부하 제어 수단**으로 보는 것이 맞다. 큐가 있어도 DB 쪽 방어는 빠지면 안 된다. 레거시 경로가 큐를 우회하기 때문이다.
- 이번 범위에서는 조건부 UPDATE를 선택하고, 큐는 "트래픽이 DB 한계를 넘을 때의 다음 단계"로 ADR에 남기는 구성이 과제 제약(별도 인프라 없음)과 맞는다.
- 조건부 UPDATE에서 함께 정해야 할 것: 여러 상품 주문은 상품 코드 순으로 차감하고 하나라도 실패하면 전체 롤백한다. 재고가 0이 될 때 `SALE_STAT`을 `'02'`로 바꿀지는 레거시 동작을 모르므로 가정이 필요하다.
- 남는 위험: 레거시 주문 경로가 "읽고 덮어쓰기"로 재고를 쓴다면 신규가 차감한 값을 레거시가 덮어써 버릴 수 있다. 신규 쪽에서 막을 수 없는 문제이므로 가정과 한계로 명시한다.

### 4.4 가격·판매 일정 분리 없이 이번 단계를 처리할 수 있는가

**처리할 수 있다.** 가격·일정 테이블 분리는 이번 범위에서 하지 않는 편이 낫다.

이유:

- 주문 흐름에 필요한 것은 "주문 시점의 가격을 확정하고 보존하는 것"이다. 레거시도 `TB_ORDER_ITEM.ORD_PRC`로 이미 하고 있고, 신규 주문 품목에 단가를 스냅샷으로 저장하면 이후 가격이 바뀌어도 주문은 영향받지 않는다.
- 가격의 원본은 레거시 `TB_GOODS.SALE_PRC` 한 곳으로 유지된다. 운영자가 어떤 도구로 가격을 바꾸든 신규 시스템은 주문 시점에 읽기만 하면 된다. 가격 테이블을 신규로 가져오면 가격 변경 경로까지 전환해야 해서 범위가 커진다.
- 세일 일정은 레거시가 지금도 누군가(운영자 또는 배치)가 `SALE_PRC`를 바꾸는 방식으로 처리하고 있을 것이다(추정). 그 방식은 그대로 동작한다.

대신 반드시 넣어야 할 것:

1. **가격 확정은 서버가 주문 시점에 한다.** 장바구니에는 가격을 권위 있는 값으로 저장하지 않는다. 담은 시점 가격은 "가격이 바뀌었습니다" 안내용으로만 쓴다.
2. **사용자가 본 금액과 다르면 주문을 거절한다.** 클라이언트가 확인한 총액을 함께 보내고, 서버가 다시 계산한 값과 다르면 재확인을 요구한다. 주문 확인 화면과 결제 사이에 가격이 오른 경우를 막는다.
3. **가격 조회와 재고 차감 사이의 틈.** 같은 레거시 트랜잭션 안에서 가격을 읽고 재고를 차감하면 일관된다. `UPDATE ... RETURNING SALE_PRC`로 차감과 동시에 가격을 가져올 수도 있다.

한계로 적어 둘 것:

- 가격 이력이 없으므로 "이 주문이 당시 올바른 가격으로 결제됐는가"는 사후 검증할 수 없다. 주문 품목 스냅샷이 유일한 기록이다.
- `UPD_DT`는 가격 버전으로 쓸 수 없다. D8에서 보듯 무엇이 바뀔 때 갱신되는지 불명확하다.
- 가격과 재고가 같은 행이다. 레거시의 가격 변경이 행 전체를 덮어쓰는 방식이면 신규가 차감한 재고를 되돌릴 수 있다. "레거시의 가격 변경은 가격 컬럼만 갱신한다"가 가정이다.
- 가격·일정 분리는 상품·재고를 신규로 옮기는 다음 단계의 과제로 남긴다.

### 4.5 복합 결제 부분 실패 시 전체 롤백 + 취소 요청

**방향은 맞다.** "전부 성공하거나 전부 없던 일로"는 사용자에게 가장 설명하기 쉽고 정산도 단순하다. 다만 "롤백"이라는 말이 가리는 부분을 설계에서 다뤄야 한다.

1. **외부 승인은 DB 롤백으로 되돌릴 수 없다.** PG와 제휴 포인트는 취소 요청이라는 별도 거래로만 되돌린다. 따라서 결제 전체를 하나의 DB 트랜잭션으로 감싸면 안 된다. 실패 시 트랜잭션이 롤백되면 "PG 승인을 받았다"는 기록까지 사라져 취소할 근거가 없어진다. **단계마다 상태를 커밋**해야 한다.
2. **호출 전에 의도를 먼저 기록한다.** 수단별로 행을 두고 `요청됨 → 승인됨 / 실패 / 불명 → 취소 요청됨 → 취소됨` 상태를 남긴다. 레거시 `TB_PAY`가 못 하는 것이 정확히 이것이다.
3. **타임아웃은 실패가 아니라 "모름"이다.** PG가 승인했는데 응답만 못 받았을 수 있다. 실패로 단정하고 끝내면 돈만 빠져나간다. 조회 후 판단하거나, 멱등한 취소를 보낸다.
4. **보상(취소)도 실패한다.** 재시도 대상으로 남기고, 일정 횟수 후에는 수동 처리 대상으로 넘긴다. "취소 요청을 보냈다"로 끝나지 않고 "취소가 확인됐다"까지 추적해야 한다.
5. **순서를 정하면 보상이 줄어든다.** 되돌리기 쉬운 것을 먼저, 어려운 것을 나중에 한다. 쿠폰과 내부 포인트(로컬 DB, 즉시 원복 가능) → 제휴 포인트 → PG 순서면, PG가 실패했을 때 되돌릴 외부 거래가 제휴 포인트 하나뿐이다. PG가 마지막에 성공하면 보상할 것이 없다.
6. **수단별 멱등 키.** 재시도해도 승인·취소가 한 번만 일어나야 한다.
7. **가상계좌는 비동기다.** 입금 전까지 쿠폰·포인트·재고를 잡아 두어야 하고, 기한이 지나면 풀어야 한다. "일부 성공, 나머지 대기"가 정상 상태인 경우가 있다는 뜻이다.
8. **재고도 같은 흐름에 속한다.** 결제 실패 시 차감한 재고를 되돌리는 것도 보상의 일부다.

고려해 볼 대안: 실패한 수단만 다시 시도하게 하고 성공한 수단은 잠시 유지하는 방식. 사용자 편의는 좋지만 상태가 늘고 방치된 승인 건을 정리하는 로직이 필요하다. 전체 취소가 더 단순하므로 이번 범위에서는 전체 취소를 택하고 이 대안은 ADR의 "버린 대안"으로 적는 것이 적절하다.

함께 정해야 할 정책: 부분 취소 시 수단별 환불 배분과 절사 규칙. D3이 보여 주듯 레거시는 여기서 이미 어긋나 있다.

### 4.6 레거시 DB와 신규 DB에 걸친 쓰기 설계 제안

전제: 두 DB를 하나의 트랜잭션으로 묶는 수단은 없다고 본다. SQLite의 `ATTACH`로는 가능하지만(3.1) 실제 환경을 대표하지 않으므로 쓰지 않는다. 목표는 "동시에 반영"이 아니라 **"어디서 끊겨도 결국 한 방향으로 수렴"**이다.

제안하는 구조:

```
1. [신규 DB] 주문을 PENDING으로 기록 + 레거시에 요청할 작업 내용 저장   → 커밋
2. [레거시 DB] 재고 차감 + 쿠폰 사용 + 포인트 차감 + 적용 표식 기록      → 한 트랜잭션으로 커밋
3. [신규 DB] 주문을 RESERVED로 변경                                      → 커밋
   (이후 외부 결제 → 4.5의 흐름)
```

핵심 장치:

1. **신규 DB에 먼저 쓴다.** 주문 의도가 남아 있어야 이후 어디서 끊겨도 "처리하다 만 주문"을 찾을 수 있다. 레거시부터 쓰면 재고만 빠지고 흔적이 없는 상태가 생긴다.
2. **레거시 쪽 작업은 로컬 트랜잭션 하나로 묶는다.** 재고·쿠폰·포인트가 모두 레거시에 있다는 4.2의 분리가 여기서 이점이 된다. 레거시 안에서는 전부 반영되거나 전부 안 된다.
3. **레거시에 적용 표식을 남긴다.** 2번 트랜잭션 안에서 "주문번호 X의 차감을 적용함"을 함께 기록한다(주문번호를 PK로 하는 작은 테이블). 이것이 두 가지를 해결한다.
   - 멱등성: 같은 주문번호로 다시 실행하면 PK 충돌로 차감이 반복되지 않는다.
   - 복구 판단: 2번과 3번 사이에서 죽었을 때, 표식이 있으면 "레거시는 반영됨"이므로 3번만 마저 하면 된다. 표식이 없으면 반영 안 된 것이므로 재시도하거나 주문을 실패 처리한다.
4. **복구 작업자.** 일정 시간 넘게 PENDING인 주문을 찾아 레거시의 표식을 확인하고 앞으로 진행하거나 취소한다. 정상 흐름과 같은 멱등 연산을 재사용한다.
5. **보상도 같은 방식.** 결제 실패로 재고를 되돌릴 때도 "주문번호 X의 차감을 원복함"을 표식으로 남겨 두 번 되돌리지 않는다.
6. **대사.** 주기적으로 신규 주문과 레거시 표식을 대조해 어긋난 건을 찾아낸다. 위 장치들이 놓친 경우의 마지막 안전망이다.

실패 지점별 결과:

| 끊긴 위치 | 상태 | 복구 |
|---|---|---|
| 1 이전 | 아무것도 없음 | 불필요 |
| 1과 2 사이 | 신규 PENDING, 레거시 표식 없음 | 재시도 또는 주문 실패 처리 |
| 2와 3 사이 | 신규 PENDING, 레거시 표식 있음 | 3을 마저 수행 |
| 3 이후 | 일치 | 불필요 |

필요한 가정: **레거시 DB에 표식용 테이블 하나를 추가할 수 있다.** 기존 테이블은 건드리지 않는 추가이므로 무중단 조건과 충돌하지 않지만, 레거시 스키마를 일절 바꿀 수 없다는 제약이 있다면 성립하지 않는다. 그 경우 쿠폰은 `USE_ORD_NO`를 표식으로 쓸 수 있으나 재고에는 대체 수단이 없다. DESIGN.md에 가정으로 밝혀야 한다.

이 구조는 3.2의 후보 C 구현 그대로이며, SQLite 파일 두 개로 각 실패 지점을 주입해 테스트할 수 있다.

### 4.7 추가로 이슈가 될 내용

**전환과 공존**

1. **주문번호 충돌.** 레거시와 신규가 같은 `ORD + 날짜 + 일련번호` 규칙으로 채번하면 겹친다. 신규는 다른 접두어나 별도 체계를 쓰고, 레거시로 역기록할 때 PK 충돌이 없는지 확인해야 한다.
2. **트래픽 전환 방식과 되돌리기.** 회원 단위나 비율로 신규 경로를 여는 스위치, 그리고 신규에서 만든 주문이 있는 상태에서 레거시로 되돌릴 때 그 주문을 어떻게 할지.
3. **레거시 주문 경로의 재고 쓰기 방식.** 4.3에서 언급한 덮어쓰기 위험. 신규가 아무리 정확해도 레거시가 잘못 쓰면 초과 판매가 난다.
4. **레거시 데이터를 믿는 범위.** D1처럼 상태가 틀린 행이 있으므로, 신규가 레거시 주문·결제를 읽는 경우 주문 상태와 결제 행을 교차 확인하는 규칙이 필요하다.

**주문·결제**

5. **재고를 언제 차감하는가.** 주문 생성 시점인지 결제 완료 시점인지. 주문 시점에 차감하면 결제하지 않은 주문이 재고를 붙잡고, 결제 시점에 차감하면 결제 후 품절이 난다. 주문 시점에 차감하고 미결제 주문은 시간 제한으로 풀어 주는 구성이 일반적이다.
6. **결제 대기 주문의 만료.** 가상계좌 기한 초과, 결제 창 이탈 시 재고·쿠폰·포인트를 되돌리는 주체가 필요하다.
7. **쿠폰 중복 사용.** 같은 쿠폰으로 두 주문이 동시에 들어오는 경우. 재고와 같은 조건부 UPDATE(`WHERE USE_YN = 'N'`)로 막는다.
8. **포인트 음수.** 포인트도 조건부 차감이 필요하다. 원장이 없으니 신규 쪽에 사용 내역을 남겨 두면 나중에 대사가 가능해진다.
9. **PG 통지 중복·역전.** 승인 통지가 두 번 오거나 취소 통지가 승인보다 먼저 오는 경우. 상태 전이를 조건부로 처리한다.
10. **취소와 부분 환불.** 과제 범위는 장바구니 → 주문 → 결제지만, 결제 실패 보상이 사실상 취소 경로다. 전체 취소·부분 취소를 범위에 넣을지 뺄지를 명시해야 한다. 뺀다면 D2~D6을 근거로 "레거시의 취소 정책이 불명확해 다음 단계로 미룬다"고 적을 수 있다.
11. **금액 계산의 단일 지점.** 주문 금액, 할인, 결제 수단별 금액의 합이 맞는지 한 곳에서 검증한다. 레거시는 제약이 없다.

**과제 수행**

12. **SQLite 테스트의 대표성.** 3.1의 제약을 DESIGN.md에 적어, 테스트가 증명하는 범위와 증명하지 못하는 범위를 구분한다.
13. **범위 관리.** 요구사항 3은 "하나를 골라"이다. 여러 개를 얕게 구현하는 것보다 하나를 실패 경우까지 다루는 편이 평가 기준에 맞는다. 구현하지 않은 위험은 DESIGN.md에서 인지하고 있음을 보이면 된다.
14. **프롬프트 기록.** 1.7 참고. 실격 사유이므로 누락이 없어야 한다.
15. **AI 제안의 채택·거부 기록.** `AI_REFLECTION.md`는 "거부·수정한 제안과 이유"를 요구한다. 이 문서의 검토 의견 중 받아들이지 않는 것이 있으면 그 이유가 곧 재료가 된다.
