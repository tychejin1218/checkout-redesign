# ADR 0004. 동일 상품 동시 주문의 재고 차감 방식

- 상태: 채택

## 맥락

과제 배경은 "세일·오픈 시점에 동일 상품으로 주문이 몰린다"고 한다. 같은 상품 행(`TB_GOODS.STOCK_QTY`)에 동시 쓰기가 집중된다.

재고를 읽고, 충분한지 확인하고, 줄인 값을 다시 쓰는 방식은 두 요청이 같은 값을 읽으면 둘 다 통과한다. 재고 3개에 요청이 몰리면 3개보다 많이 팔린다. 레거시 테이블에는 음수 재고를 막는 제약도 없다.

조건이 둘 더 있다.

- **재고의 원본은 레거시 DB다**(ADR 0002). 레거시 주문 경로도 같은 재고를 차감한다고 가정한다. 신규 시스템 안에서만 통하는 보호 장치는 레거시 경로를 막지 못한다.
- **재고 차감은 레거시 트랜잭션의 일부다**(ADR 0003). 반영 기록, 쿠폰, 포인트와 함께 한 트랜잭션으로 실행되고, 하나라도 실패하면 전부 롤백돼야 한다.

구현 환경인 SQLite에는 행 잠금이 없다. `SELECT ... FOR UPDATE`는 문법 오류다.

## 고려한 대안

| | 대안 | 내용 |
|---|---|---|
| A | 큐로 직렬화 | 주문 요청을 상품별 큐에 넣고 한 건씩 처리한다 |
| B | 비관적 잠금 | 재고 행을 잠그고 읽은 뒤 차감한다 |
| C | 조건부 UPDATE | `SET STOCK_QTY = STOCK_QTY - n WHERE STOCK_QTY >= n`, 영향 행 수로 성공 판정 |

## 선택과 근거

**C를 고른다.**

```sql
UPDATE TB_GOODS
   SET STOCK_QTY = STOCK_QTY - #{qty}
 WHERE GOODS_CD = #{goodsCd}
   AND SALE_STAT = '01'
   AND STOCK_QTY >= #{qty}
   AND SALE_PRC = #{expectedPrice}
```

1. **읽고 덮어쓰지 않는다.** 확인과 차감이 문장 하나이므로 두 요청이 같은 값을 보고 둘 다 통과하는 일이 없다. 조건 때문에 재고가 음수가 될 수 없다.
2. **DB 문장 수준의 보호다.** 큐나 애플리케이션 잠금과 달리, 신규 시스템을 거치지 않는 쓰기와 섞여도 이 문장 자체는 음수를 만들지 않는다.
3. **잠금 보유 시간이 가장 짧다.** 문장 하나만큼만 잡는다.
4. **추가 인프라가 없다.** 과제 제약(별도 인프라 없이 실행)과 맞는다.
5. **다른 조건을 같은 문장에 실을 수 있다.** 판매 상태와 가격을 함께 확인한다. 금액을 계산한 뒤 차감하기 전에 가격이 바뀌면 차감이 실패한다. 가격을 별도 테이블로 나누지 않고도 "운영 중 가격 변동"을 막는다.
6. **쿠폰과 포인트에도 같은 방식을 쓴다.** `WHERE USE_YN = 'N'`, `WHERE POINT_AMT >= ?`로 중복 사용과 음수 잔액을 막는다.

여러 상품을 담은 주문은 상품 코드 순으로 차감하고, 하나라도 영향 행 수가 0이면 레거시 트랜잭션 전체를 롤백한다. 실패했을 때는 그 상품을 다시 읽어 이유(상품 없음, 판매 중 아님, 가격 변동, 재고 부족)를 구분한다.

**함께 정한 것: 트랜잭션은 시작할 때 쓰기 잠금을 잡는다(`BEGIN IMMEDIATE`).** SQLite의 기본 방식(`BEGIN DEFERRED`)은 트랜잭션을 시작할 때 잠금을 잡지 않고 처음 쓰는 문장에서 잡는다. 이 방식에서는 읽고 나서 쓰려는 트랜잭션 둘이 만나면 서로를 기다리는 상태가 되어, 대기 시간 설정(`busy_timeout`)과 무관하게 한쪽이 즉시 실패한다. `BEGIN IMMEDIATE`는 시작하는 시점에 그 DB 파일의 쓰기 잠금을 잡는다. 다른 쓰기 트랜잭션은 시작 지점에서 `busy_timeout`(5초)만큼 기다렸다가 차례로 들어오고, 읽기는 막지 않는다. 그 결과 한 DB 파일의 쓰기 트랜잭션은 한 번에 하나씩 실행된다. 두 DataSource 모두 이 방식으로 연다(`transaction_mode=IMMEDIATE`).

이 설정은 SQLite에서 동시 요청이 오류 없이 줄을 서게 하는 장치이고, 초과 판매를 막는 것은 여전히 조건부 UPDATE다. 행 잠금이 있는 운영 DB에서는 이 설정이 필요 없고 조건부 UPDATE만으로 같은 결과가 나온다.

재고 3개인 상품에 20건이 동시에 주문하면 3건만 성공하고 재고가 0이 되는 것을 테스트로 확인했다(`OrderConcurrencyTest`).

## 버린 이유와 trade-off

**A(큐)를 정확성 수단으로 쓰지 않은 이유.** 큐는 순간 부하를 흡수하고 선착순을 보장하며 대기열 화면을 붙일 수 있다. 버린 이유는 이렇다.

- 레거시 주문 경로는 큐를 거치지 않는다. 큐만으로는 초과 판매를 막지 못하므로 DB 쪽 보호가 어차피 필요하다.
- 별도 인프라가 필요하고, 큐 자체의 유실·중복을 다뤄야 한다.
- 응답이 비동기가 되어 주문 흐름과 화면이 복잡해진다.

큐를 완전히 버린 것은 아니다. 정확성 수단이 아니라 **부하 제어 수단**으로 본다. 트래픽이 DB 한계를 넘는 단계가 되면 조건부 UPDATE 앞에 붙인다.

**B(비관적 잠금)를 버린 이유.** 읽은 값으로 복잡한 검증을 할 수 있고 이해하기 쉽다. 그러나 인기 상품 행 하나에 대기가 줄을 서고, 여러 상품 주문에서 교착이 생길 수 있으며, 레거시도 같은 방식으로 잠가야만 효과가 있다. SQLite에서는 표현할 수도 없다.

**치르는 비용:**

- **실패 이유가 문장에서 나오지 않는다.** 영향 행 수 0은 "조건에 안 맞음"일 뿐이라, 이유를 알려면 한 번 더 읽어야 한다.
- **선착순이 엄밀하지 않다.** 먼저 요청한 사람이 아니라 먼저 DB에 도달한 문장이 재고를 가져간다.
- **재고를 쥐고 있는 미결제 주문이 생긴다.** 주문 시점에 차감하므로 결제하지 않은 주문이 재고를 붙잡는다. 제한 시간 5분이 지나면 되돌린다(가정 5). 세일 시점에 결제하지 않는 주문이 재고를 묶어 두는 시간을 줄이려고 짧게 잡았다. 대신 결제에 5분 넘게 걸리는 사용자는 주문이 취소되고, 입금이 나중에 이뤄지는 가상계좌는 이 값으로 다룰 수 없어 수단별 기한이 따로 필요하다(ADR 0005).
- **SQLite에서는 쓰기 트랜잭션이 한 번에 하나다.** `BEGIN IMMEDIATE` 때문에 같은 DB 파일의 쓰기는 상품이 달라도 줄을 선다. 대기가 `busy_timeout`을 넘으면 그 요청은 실패한다.
- **`SALE_STAT`은 바꾸지 않는다.** 재고가 0이 돼도 품절 코드로 바꾸지 않는다. 레거시가 이 코드를 누가 언제 되돌리는지 알 수 없어서다. 레거시 화면이 `SALE_STAT`만 본다면 재고 0인 상품이 판매 중으로 보인다(가정 6).
- **레거시가 재고를 읽고 덮어쓰는 방식이라면 보호되지 않는다.** 신규가 차감한 값을 레거시가 예전 값으로 덮어쓸 수 있고, 신규 쪽에서는 막을 수 없다(가정 3, 4).
- **SQLite 테스트는 정확성만 증명한다.** SQLite는 쓰기를 DB 파일 단위로 직렬화하므로, 운영 DB에서 인기 상품 행에 걸리는 잠금 경합과 처리량은 이 테스트로 알 수 없다.
