# ADR 0001. 구현으로 증명할 가장 위험한 지점

- 상태: 채택

## 맥락

과제는 설계에서 가장 위험하다고 판단한 지점 **하나**를 골라 실행 가능한 코드와 테스트로 증명하라고 요구한다. 전체를 구현할 필요는 없고, 기한은 3일이다.

과제 배경이 직접 언급하는 위험은 넷이다.

- 세일·오픈 시점에 동일 상품으로 주문이 몰린다.
- 상품 가격이 운영 중 수시로 바뀐다.
- 하나의 결제에 외부 PG, 제휴 포인트, 내부 포인트, 쿠폰이 함께 쓰인다.
- 전환 기간 동안 레거시 DB와 신규 시스템이 공존한다.

레거시 데이터에는 이미 문제가 일어난 흔적이 있다. 결제 행이 미결제인데 주문은 결제완료인 건(`ORD20260301004`), 취소됐는데 쿠폰이 사용 상태로 남은 건(`ORD20260228009`)이 그렇다. 주문 상태와 그에 딸린 자원의 상태가 따로 움직이고 있다.

구현 환경은 SQLite3이다. 행 잠금이 없고 쓰기가 DB 파일 단위로 직렬화되므로, 무엇을 고르든 "이 환경에서 무엇을 증명할 수 있는가"가 선택에 영향을 준다.

## 고려한 대안

| | 후보 | 위험 |
|---|---|---|
| A | 재고 초과 판매 | 재고 3개에 100건이 동시에 들어와 3개보다 많이 팔린다 |
| B | 복합 결제의 부분 실패 | PG는 승인됐는데 제휴 포인트는 실패해, 돈은 나갔는데 주문이 없다 |
| C | 두 DB에 걸친 쓰기의 부분 반영 | 주문은 신규 DB에 있는데 레거시 재고는 안 빠졌거나, 그 반대 |
| D | 중복 요청 | 재시도나 중복 클릭으로 같은 주문의 재고가 두 번 빠진다 |

## 선택과 근거

**C를 고른다.** A의 조건부 재고 차감과 D의 멱등성은 C의 구현 안에 포함한다. B는 설계로만 다룬다(ADR 0005).

**고른 이유.** 이 흐름에서 가장 중요한 것은 데이터 정합성이다. 레거시 DB와 신규 DB는 한 트랜잭션으로 묶을 수 없어서, 한쪽만 반영되어도 DB가 막아 주지 못한다. 그리고 이 위험은 공존 기간 내내 이어지므로 그동안 계속 주의가 필요하다.

이 판단을 뒷받침하는 점은 다음과 같다.

1. **스스로 드러나지 않는 실패다.** A와 D는 한 DB 안에서 일어나므로 제약이나 조건으로 그 자리에서 막을 수 있다. B는 외부 시스템이 걸려 있어 여기에 해당하지 않는다. C는 두 DB의 커밋 사이에서 프로세스가 죽으면 어느 쪽 DB도 불일치를 알지 못한다. 별도의 장치가 없으면 발견조차 되지 않는다.
2. **공존 기간 내내 모든 주문에서 일어날 수 있다.** 주문을 신규 DB에, 재고를 레거시 DB에 두는 한(ADR 0002) 모든 주문이 DB 간 쓰기다. 가장 자주 지나가는 경로가 곧 위험 경로다.
3. **과제의 요구사항 2와 직접 이어진다.** "레거시 DB와 신규 DB를 어떻게 나누고 공존 기간에 데이터를 어떻게 다룰지"에 대한 답을 코드로 보이는 것이 된다.
4. **SQLite에서 충실하게 재현된다.** DB 파일 두 개를 별도 커넥션으로 열고 두 커밋 사이에 실패를 주입하면 실제 문제와 같은 상태가 만들어진다. A는 SQLite가 쓰기를 직렬화하므로 정확성은 보일 수 있어도 잠금 경합은 재현되지 않고, B는 외부 시스템을 전부 가짜로 대신해야 한다.
5. **하나의 시나리오로 A와 D까지 다룬다.** "신규 DB에 주문 기록 + 레거시 DB에서 재고 차감"을 구현하면 동시 주문과 재시도가 같은 코드에서 검증된다.

## 버린 이유와 trade-off

**A(재고 초과 판매)를 단독 주제로 삼지 않은 이유.** 과제가 직접 언급한 문제이고 설명하기 쉽다. 하지만 해법(조건부 UPDATE)이 잘 알려져 있어 판단이 드러날 여지가 작고, SQLite에서는 운영 DB의 행 잠금 경합을 보일 수 없다. 버리지 않고 C의 레거시 트랜잭션 안에 넣었다.

**B(복합 결제)를 구현하지 않은 이유.** 돈이 직접 걸린 위험이고 레거시 데이터의 증거도 가장 강하다. 그러나 구현하려면 PG와 제휴사를 가짜로 만들어야 하고, 증명의 무게가 "가짜 외부 시스템이 실제와 같다"는 가정에 실린다. 3일 안에 C와 B를 둘 다 하면 둘 다 얕아진다.

**D(멱등성)를 단독 주제로 삼지 않은 이유.** 범위가 좁다. C에서 레거시 반영 기록과 회원별 멱등 키로 자연스럽게 다뤄진다.

**치르는 비용:**

- 결제 흐름이 코드에 없다. 결제 실패는 취소 서비스를 직접 호출하는 것으로 대신하므로, "외부 승인이 타임아웃됐을 때"와 같은 B의 어려운 경우는 테스트되지 않는다.
- 프로세스 강제 종료를 실패 주입으로 흉내 낸다. 커밋 도중의 중단은 SQLite의 원자적 커밋에 맡기고 재현하지 않는다.
- 테스트가 증명하는 것은 절차의 정확성이다. 운영 DB에서의 처리량과 잠금 경합은 증명하지 않는다.
