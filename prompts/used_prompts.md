# 사용한 프롬프트

- 도구: Claude Code (데스크톱 앱), 모델 Claude Fable 5.2
- 기록 방식: 입력한 프롬프트를 순서대로 원문 그대로 적는다. 각 프롬프트 아래의 "결과"는 맥락 파악을 위한 한두 줄 요약이다.
- AI가 제시한 선택지 버튼을 눌러 답한 경우도 프롬프트로 기록하고, 어떤 질문에 대한 답이었는지 함께 적는다.

## 1. 과제 분석 요청

```text
해당 폴더에 assignment/과제_장바구니주문결제_지원자배포.pdf 와 assignment/legacy_db.sql 을 읽고 분석해줘
이번에는 아래 두 파일만 만들고, 설계 문서나 코드는 아직 만들지 마.

만들 파일
- assignment/assignment.md : PDF 내용을 요약하거나 해석을 추가하지 말고 마크다운으로 변환한 내용을 추가해줘
- assignment/analysis.md : 분석한 내용을 정리해줘. 확인 요청에 대한 내용을 따로 정리해줘

분석할 것
1. 요구사항, 제출물, 기술 제약, 제출, 실격 요건을 정리해줘
2. legacy_db.sql 
 2_1. 스키마 구조상 문제가 있는지 검토하고 정리해줘
 2_2. 데이터에서 정합성이 깨진 곳이 있는지 검토하고 어떤 테이블에 어떤 행인지 정리해줘 
3. 가장 위험한 지점 후보 3~4개 정리해주고, SQLite 환경에서 테스트가 가능한지도 확인해줘

확인 요청
1. 배경의 서비스 무중단, 레거시 DB 와 신규 시스템 공존은 신규 DB 로 한 번에 모두 마이그레이션 하지말고 순차적으로 전환하라는 의도로 해석했는데, 맞는지 검토해줘
2. 1번이 맞다면, 이번 범위에서는 재고, 포인트, 쿠폰은 레거시 DB 에 두고 주문, 결제, 장바구니는 신규 DB 로 구성한 뒤, 레거시에 남은 것은 이후 단계에서 순차적으로 신규 DB 로 옮기는 방향을 생각했는데 어떤지 검토해줘
3. 세일, 오픈 시점에 동일 상품으로 주문이 몰리는 부분은 앞단에 큐로 직렬화하거나, DB 잠금을 쓰거나, 조건부 UPDATE 를 해야 할 것 같은데 장단점을 검토해줘
4. 상품 가격이 운영 중에 바뀌는 경우를 대비해 가격과 판매 일정을 별도 테이블로 나눠 관리해야 할 것 같은데, 이번 단계에서는 레거시 상품 테이블에 가격과 재고가 묶인 채로 처리할 수 있는지 검토해줘
5. 하나의 결제에 외부 PG, 포인트, 쿠폰 등이 함께 적용될 때 일부 수단만 성공하고 나머지가 실패하는 경우 성공한 내용도 롤백 처리 및 취소 요청을 보내서 실패 처리하려고 하는데 검토해줘
6. 레거시 DB와 신규 DB를 같이 사용할 때 쓰기 트랜잭션에서 한 쪽만 반영되는 경우 이슈가 될 것 같은데 어떤식으로 설계하면 좋을지 제안해줘
7. 추가적으로 이슈가 될 내용들은 검토해서 정리해줘
```

결과: `assignment/assignment.md`(PDF 변환), `assignment/analysis.md`(과제 정리, 스키마·데이터 검토, 위험 지점 후보 A~D, 확인 요청 1~7 검토) 생성. AI는 위험 지점 후보 중 C를 권했다.

## 10. ADR 검토 결과 반영 요청

```text
0001
- C 를 고른 이유는 다음과 같은 이유로 변경해줘: 데이터 정합성이 가장 중요한데, 레거시 DB 와 신규 DB 는 한 트랜잭션으로 묶을 수 없어서 한쪽만 반영되어도 DB 에서 막을 수 없고, 공존 기간 내내 주의가 필요하기 때문이다
- 근거 1의 "A, B, D 는 그 자리에서 막을 수 있다"에서 B 는 외부 시스템이 걸려 있어 해당하지 않으니 제외해줘

0003
- 이해한 흐름은 다음과 같은지 확인해주고 실제 코드와도 동일한지 확인 후 다르면 알려줘 
  1. 신규 DB 에 주문을 대기 중(PENDING) 으로 기록
  2. 레거시 DB 에서 재고, 포인트, 쿠폰을 차감하고 표식을 추가 (레거시 트랜잭션 하나)
  3. 신규 DB 의 주문 상태를 확보 성공(RESERVED) 으로 변경. 2번이 실패하면 확보 실패(FAILED)
- 재고, 포인트, 쿠폰의 확보 상태를 따로 나눠야 할 것 같았는데 상세 상태는 고도화 시에 나누면 될 것 같으니 그렇게 적어줘
- "같은 주문번호로 다시 실행하면 아무것도 바꾸지 않는다"는 차감에 성공한 주문에만 해당하니 그에 맞게 고쳐줘
- 주문을 처음 기록할 때 덮어쓰지 않고 INSERT 로만 한다는 결정을 ADR 에 추가해줘
- 표식이라는 단어가 어색하니 DESIGN.md, adr/, docs/erd, 코드 주석에서 "반영 기록"으로 바꿔줘. "거부 표식"은 "거부 기록"으로 바꿔줘. 클래스나 메서드 이름은 바꾸지 마
- 거절된 주문에 거부 반영 기록이 남지 않는 점은 코드를 고치지 말고 한계로 적어줘

0004
- 낙관적 잠금을 하려면 레거시 테이블에 버전 컬럼을 추가해야 하지 않아? 그렇다면 ADR 에서 제거해줘
- BEGIN IMMEDIATE 가 시작할 때부터 쓰기 잠금을 잡는 건가? 그렇다면 그 결정을 ADR 에 추가하고 DESIGN.md 내용을 맞춰줘
- 미결제 주문의 재고 점유 시간 30분은 너무 긴 것 같으니 5분으로 줄여줘. 이 값을 쓰는 코드, 테스트, DESIGN.md 도 같이 맞춰줘

0005
- 결제 순서의 근거를 다음과 같이 변경해줘. 외부 결제는 우리가 통제할 수 없는 부분이니 뒤에 두고, 우리가 통제할 수 있는 내부 포인트와 쿠폰을 먼저 처리한다. 지금 순서가 이 기준과 맞는지 확인하고, 다르면 알려줘
- 외부 결제끼리의 순서(제휴 포인트 → PG)는 지금대로 유지하고, "되돌리기 쉬운 것 먼저"와 "실패가 잦은 것 먼저"의 trade-off 를 적어줘

공통
- ADR 의 멱등 키는 회원별로 유일하다는 점을 반영해줘
- 주문 시 회원이 존재하는지 확인하도록 코드를 수정하고 테스트를 추가해줘. DESIGN.md 도 내용을 맞춰줘

수정 후 ./gradlew test 가 통과하는지 확인해줘
```

결과: ADR 5건과 DESIGN.md, docs/erd, 코드 주석을 요청대로 고쳤다. 회원 확인(`LegacyMemberPort`)과 테스트를 추가했고 미결제 제한 시간을 5분으로 줄였다. `./gradlew test` 63건 통과, `./gradlew build` 통과.

## 17. 복구 루프 예외 격리 · 멱등 키 내용 검증 · 금액 Long 전환 · 문서 동기화 스킬 요청

```text
1. OrderRecoveryService.recoverStuckOrders 는 한 주문에서 예외가 발생하면 뒤의 주문이 복구되지 않는 것 같은데 확인해줘
맞다면 주문 한 건의 실패가 나머지 복구를 막지 않도록 주문별로 예외를 잡아 로그를 남기고 다음 주문으로 넘어가게 해줘
cancelUnpaidOrders 도 같은 문제가 있는 것 같은데 같이 확인해줘

2. 같은 회원이 같은 멱등 키로 다른 내용(품목, 수량, 쿠폰, 포인트)의 요청을 보내면 지금은 기존 주문을 그대로 돌려주는데,
이 경우는 거절하도록 해줘 같은 내용이면 지금처럼 기존 주문을 돌려줘

3. OrderQuoteService 의 qty * unitPrice 가 Int 라서 수량이 크면 넘칠 수 있어. 금액은 Long 타입으로 변경해줘
단가, 합계, 금액 등이 대상이고 수량은 Int 로 유지해줘
금액을 다루는 곳을 전체 검사해서 빠진 곳이 없게 해주고, 바꾼 곳을 목록으로 알려줘
DB 스키마는 바꿀 필요가 있는지 확인만 해줘

4. 코드를 수정하면 DESIGN.md 와 docs/order-flow.md 에 반영하는 절차를 프로젝트 스킬로 만들어줘
- 스킬 내용: src/main 이나 src/test 의 코드가 바뀌면 DESIGN.md
- 훅: 응답을 끝내기 전에, 이번 작업에서 src 아래 코드가 바뀌었는데 두 문서가 바뀌지 않았으면 이 스킬을 실행하라고 알려주도록 .claude/settings.json 에 추가해줘
- 훅이 스킬을 직접 실행할 수 없다면 가능한 방식을 제안해주고 진행해줘
- CLAUDE.md 에도 같은 규칙을 한 줄로 적어줘
```

결과: 네 가지를 모두 반영했다. `./gradlew build` 통과(테스트 80건).

1. 두 메서드 모두 한 주문의 예외가 뒤의 주문을 막는 것이 맞았다(`cancelUnpaidOrders` 는 `ApiException` 만 잡고 있었다). 주문별로 예외를 잡아 로그를 남기고 넘어가게 했다.
2. 같은 멱등 키로 품목·수량·쿠폰·포인트가 다른 요청이 오면 `ORDER_IDEMPOTENCY_KEY_REUSED`(409)로 거절한다. 같은 내용이면 기존 주문을 돌려준다.
3. 금액(단가, 합계, 할인, 결제 금액, 포인트)을 `Long` 으로 바꿨다. 수량은 `Int` 그대로다. DB 스키마는 바꾸지 않았다(SQLite `INTEGER` 는 8바이트까지 담는다).
4. `sync-docs` 스킬(`.claude/skills/sync-docs`), Stop 훅(`.claude/hooks/docs-sync-check.sh`, `.claude/settings.json`)을 추가하고 `CLAUDE.md` 에 규칙을 적었다. 훅은 스킬을 직접 실행할 수 없어, 응답 종료를 막고 스킬을 실행하라고 알리는 방식으로 했다. 이번 변경을 `DESIGN.md` 와 `docs/order-flow.md` 에 반영했다.
